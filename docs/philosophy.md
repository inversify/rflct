# Philosophy & Motivation

## The problem

For over a decade, TypeScript's `emitDecoratorMetadata` compiler flag — paired
with the `reflect-metadata` polyfill — was the standard way to make type
information available at runtime. Dependency injection containers like
InversifyJS, TypeORM, and NestJS all relied on it: you decorated a class, and
the compiler emitted `design:paramtypes` metadata automatically.

This worked, but it was built on two experimental foundations:

1. **Experimental decorators** (`experimentalDecorators`) — a TypeScript-specific
   implementation that predates and diverges from the TC39 decorator proposal.
2. **`emitDecoratorMetadata`** — a compiler feature tightly coupled to
   experimental decorators, with no equivalent for the standard decorator
   specification.

## What changed

The TC39 decorator proposal reached Stage 3 and was adopted by the standard.
TypeScript 5.0 shipped native support for standard decorators — without the
`experimentalDecorators` flag.

Critically, **standard decorators do not support `emitDecoratorMetadata`**.
The metadata emission feature was always specific to the legacy experimental
implementation and was never part of the TC39 proposal. TypeScript 7 is expected
to remove the experimental decorator implementation entirely.

This leaves a gap: frameworks that relied on `emitDecoratorMetadata` to discover
constructor parameter types, property types, and method parameter types at
runtime have no migration path within the decorator specification itself.

## RFLCT's approach

RFLCT takes a different approach entirely: **emit type metadata at compile time
from type annotations, not from decorators**.

Instead of decorating a class and relying on the compiler to emit metadata as a
side effect, you annotate parameters and properties with `Reflect<T>` — a
zero-cost type alias that the RFLCT transformer reads during compilation:

```ts
import { Reflect } from "rflct";

class UserService {
  constructor(
    db: Reflect<Database>,
    logger: Reflect<Logger, { optional: true }>
  ) {}
}
```

The transformer produces `Reflect.defineMetadata(...)` calls that are
structurally identical to what `emitDecoratorMetadata` used to produce — no
decorators required, no experimental flags, no runtime overhead beyond the
metadata itself.

## Why `reflect-metadata` and the `design:*` keys

RFLCT deliberately uses the same runtime (`reflect-metadata`) and the same
metadata key namespace that the ecosystem already understands:

| Key | Purpose |
|-----|---------|
| `design:paramtypes` | Parameter type metadata for constructors and methods — same key that `emitDecoratorMetadata` used |
| `design:propertytype` | Property type metadata — per-property `{ type, metadata }` entries |
| `design:properties` | Property name registry (new — enables property discovery without prototype scanning) |
| `design:symbols` | Global type registry mapping qualified names to runtime identities |
| `design:class` | Class-level metadata via `Reflectable<T>` |

This is intentional. By reusing the `design:*` namespace:

- **Migration is incremental.** Existing code that reads `design:paramtypes` via
  `Reflect.getMetadata("design:paramtypes", ...)` continues to work for
  constructor and method metadata. Property metadata uses the new
  `design:propertytype` key.
- **No new runtime dependency.** The `reflect-metadata` polyfill is already
  installed in virtually every DI-aware TypeScript project.
- **Interop is possible.** Libraries can consume RFLCT metadata without knowing
  it was generated by RFLCT rather than by `emitDecoratorMetadata`.

## Design goals

1. **Universal** — works with any build tool via unplugin (Vite, Rollup, webpack,
   esbuild) and with the TypeScript 7 CLI for standalone `tsgo` projects.
2. **Generic** — not tied to any specific DI container or framework. RFLCT emits
   metadata; consumers decide what to do with it.
3. **Zero runtime cost** — `Reflect<T>` erases to `T` at the type level. The
   transformer runs at build time. The only runtime artifact is the
   `Reflect.defineMetadata` calls in the output.
4. **Type-driven** — metadata comes from type annotations, not from imperative
   decorator calls. This means interfaces and type aliases — things that don't
   exist at runtime — get stable `Symbol.for(...)` identities automatically.
5. **Migration-friendly** — same `reflect-metadata` runtime, same `design:*`
   keys, same metadata shape. Switching from `emitDecoratorMetadata` to RFLCT
   should not require rewriting metadata consumers.

## What RFLCT is not

RFLCT is not a decorator library. It does not provide decorators, does not
require decorators, and does not depend on any decorator specification — TC39 or
experimental. It is a build-time type metadata emitter that happens to produce
output compatible with the decorator metadata ecosystem.
